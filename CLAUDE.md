# kpi-platform — памятка для Claude

Платформа KPI-ботов для оптовых компаний (в основном на 1С). Один код — ядро и модули, у каждого клиента
своя папка с настройками и надстройками, свой бот, своя база, свой процесс.
Владелец — Адам («босс»). Он не программист: объяснять простыми словами и примерами, на «ты», по-русски.
Суммы писать полностью (15 323 000), без «м/т».

**Имена.** Claude Code на сервере — **Альфред** (обращается «сэр»). Claude в чате claude.ai — **Джарвис**
(обращается «босс»). В журнале пишем «(Альфред)» и «(Джарвис)».

**Теплоком.** Бот Теплокома (`quizbot`) — отдельный проект, к платформе не относится и не переезжает на неё.
Из него берём только идеи и обезличенные механизмы. Его репозиторий, сервер, базу не трогаем никогда.

## Правила (строго)

1. **Никаких изменений без «да».** Сначала коротко: что изменится и зачем. Ждём «да» — потом делаем.
   Касается и исправлений, которые нашёл сам.
2. **Ядро не знает клиентов.** В `core/` и `modules/` нет ни имён людей, ни названий фирм, ни их правил,
   ни «если клиент такой-то». Всё конкретное — в `clients/<клиент>/`. Хочется написать в ядре условие
   про конкретного клиента — значит, нужен крючок (hook) в ядре и правило в папке клиента.
3. **Код живёт в git.** GitHub `fwjn7w7cng-cloud/kpi-platform`, ветка `main` = рабочее состояние.
   Правка: ветка → тесты → fast-forward в `main` → push. Никогда `push --force` в `main`.
4. **Тесты перед каждым пушем.** `python3 -m unittest discover -s tests -v` — всё зелёное.
5. **Секреты не в git.** Токены ботов, ключи Google, пароли — только в `.env` клиента на сервере.
   Не выводить в чат, не просить Адама вставлять их в чат.
6. **Журнал `JOURNAL.md` обязателен.** Перед работой — прочитать верхние записи и `git log --oneline -10`.
   После заметной работы — запись сверху: дата и время по Москве, кто, 1–3 строки (что сделано, что найдено,
   что осталось). Это единственный мост между Джарвисом и Альфредом.
7. **Шаги на сервере — по одному**, команды — в отдельном блоке, каждый раз целиком.
8. **Сервер пока не трогаем** (решение Адама 27.10): строим основу в репозитории и гоняем тесты в чате.

## Как устроено

```
core/                   ядро — одно на всех, клиентов не знает
  config.py             анкета клиента (config.yaml): чтение и проверка, ошибки по-русски все сразу
  hooks.py              крючки: куда клиент вставляет свои правила и кубики зарплаты (rules.py)
  calendar.py           рабочие дни: выходные и праздники из анкеты, «нужно к сегодня»
  app.py                приложение клиента: анкета + база + экраны; start / press / text → [Reply]
  access/               роли (roles.py) и редакции с модулями (editions.py)
  data/                 нейтральный формат (model.py), база SQLite (db.py), миграции (migrations.py)
  ingest/               приём: почта (mail.py) / Диск (drive.py) → переводчик клиента → база (pipeline.py);
                        excel.py — инструменты для переводчиков (таблица, шапка 1С, месяц, ключ человека)
  kpi/                  engine.py — продажи, фокус, АКБ, SKU, сбор, визиты, просрочка, группы, свои формулы
  pay/                  components.py — кубики зарплаты; engine.py — расчёт по схеме должности + табель + правки
  month/cycle.py        открыт → согласование → утверждён; правки с причиной; ведомость Excel
  ui/                   views.py — экран картинкой/текстом/PDF; kit.py — Reply/Button; registry.py — экраны,
                        ввод текста, меню; context.py — кто смотрит и что ему видно; screens.py — экраны ядра
  jobs/                 schedule.py — рассылки по расписанию; briefs.py — утренняя сводка
  transport/            telegram.py — мессенджер; max.py — место под MAX
modules/                модули: каждый файл сам регистрирует экраны, пункты меню, рассылки
clients/<клиент>/       всё про конкретную фирму
  config.yaml           анкета: отделы, команды, должности, схемы зарплаты, KPI, табель, расписание, редакция
  parser.py             переводчик его отчётов 1С → нейтральные пачки (у demo вместо него seed.py)
  rules.py              его особые правила через крючки (по необходимости)
  .env                  секреты: BOT_TOKEN, ADMIN_IDS, почта/Диск (не в git)
clients/_template/      шаблон нового клиента — копируется при подключении
clients/demo/           вымышленная фирма для показа: seed.py (наполнитель), vocab.py (8 отраслей)
tools/                  crawl.py — робот прокликивает все роли; check_client.py — проверка анкеты и файлов клиента
deploy/kpi@.service     служба на клиента: systemctl enable --now kpi@<код>
run.py                  запуск бота клиента: python3 run.py <код>
tests/                  тесты (unittest)
```

Каждый клиент — свой бот (токен в его `.env`), свой файл базы, свой процесс. Упал один — другие живут.

## Как подключить нового клиента

1. Анкета — **таблица** (Google-таблица или Excel, листы по-русски с выпадающими списками; `core/anketa.py`).
   Пустой шаблон: `python3 tools/anketa.py blank шаблон.xlsx`; проверка: `tools/anketa.py check <файл|ссылка>`;
   запись: `tools/anketa.py apply <файл|ссылка>` — создаст `clients/<код>/` из шаблона и запишет `config.yaml`.
   config.yaml руками не правим — правим таблицу и делаем apply. Ошибки — с листом и строкой.
2. Переводчик `parser.py` — по 2–3 файлам его 1С; проверка: `python3 tools/check_client.py <код> файлы…`.
3. Своё, чего нет в ядре, — только в `rules.py` через крючки (`core/hooks.py`), ядро не трогаем.
4. Бот в @BotFather → токен в `clients/<код>/.env` вместе с ADMIN_IDS и почтой.
5. На сервере: `systemctl enable --now kpi@<код>`. Сотрудники пишут боту /start → админ привязывает заявку.

## Модули и редакции

Список и состав — `core/access/editions.py`. Модуль = файл `modules/<код>.py`: регистрирует экраны
(`@screen(id, module=…)`), пункты меню (`menu(...)`), ввод текста (`@text_input`), рассылки (`@job`).
Модуля нет в редакции клиента — пункт меню виден с замком 🔒, экран объясняет, что внутри и с какой редакции.
Новый модуль: файл в `modules/`, код в `editions.MODULES`, имя в `core/app.MODULES`, тест робота проходит.
Свободный текст (человек написал сам, бот ничего не ждал) — `@free_text(module, order)`: первая функция, что ответила
(код клиента → карточка, код товара → остаток). Сдельные кубики зарплаты `per_unit` — единицы регистрирует модуль
(`components.unit("km", fn)`), названия — `components.UNIT_TITLES`. Рассылка по дням недели — `@job(..., days=[...])`.
Тяжёлые расчёты между нажатиями — `app.memo(ctx, имя, fn)`: живёт, пока не поменялись данные (`db.rev()`).

Состав (28.10): Старт — KPI-ядро, напоминания; Бизнес — дебиторка, достижения, кабинеты персонала, зарплата, задачи,
клиенты (спящие/падают/растут/бренды), маршрут и отчёт за день, тесты и обучение; Контроль — утверждение зарплаты,
журнал, ночной сторож, прогноз, «кому позвонить», свои формулы, утверждение планов; отдельно — AI-аналитик, склад для
закупок, логистика, возвраты (+4 с замком, не сделаны). «🐞 Не работает» / предложения (`modules/feedback.py`) — у всех,
вне редакций. Отпуска и документы убраны по решению Адама 28.10.

## Показ (демо)

`source.kind: seed` — режим показа: у каждой отрасли своя база (`data/<клиент>/<отрасль>/kpi.db`),
наполняется `clients/<клиент>/seed.py`, обновляется сама в начале месяца. Зритель кнопками внизу главной
выбирает роль (или конкретного человека), отрасль (8) и редакцию (3); «Начать демо заново» — свежие цифры.

## Данные (`core/data`)

- База клиента — `data/<клиент>/kpi.db` (`client_db_path`, папку переносит `KPI_DATA`). `DB.open` сам догоняет миграции.
- Миграции — `core/data/migrations.py`: список только дописывается в конец, старые шаги не трогаем.
- Факты (`sales`, `debts`, `payments`, `visits`, `returns`, `stock`, `item_sales`, `trips`, `trip_stops`, справочники
  `clients`, `groups`) пишутся только **пачками**
  (`DB.load(Dataset)`): новая пачка того же вида за тот же период заменяет прежнюю; файл с тем же
  `fingerprint` повторно не принимается; строка с датой вне периода — вся пачка отклоняется.
- Люди в фактах — ключом источника (`emp_key`, «фамилия имя», `norm_key`: регистр, ё, пробелы).
  Ключ → сотрудник в `emp_keys` с датой `since`: новый торговый на старой территории — `bind_key(…, since=…)`,
  продажи до даты остаются прежнему. Не привязанные ключи — `unknown_keys()` («нет в расчёте»).
- Месяц: `open` → `review` → `approved` (`set_month_status`, пишет в `audit`).
